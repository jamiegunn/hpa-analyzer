Limits

Every entry below is measured rather than estimated, and each names the proof script or test that measures it. This page exists because a tool that only advertises its strengths cannot be checked, and because several of these were found by the project's own proofs contradicting the project's own README.

What it is genuinely good at

Context first, so the rest of the page is proportionate. The tool earns its place in a narrow lane:

JVM-in-container fitness — nothing else in the standard stack checks this. Applied-versus-inert JAVA_OPTS with correct Docker exec/shell/CMD-form semantics, reading pod-spec env and an in-directory entrypoint script before calling a flag "missing"; Java 8 update-level cgroup awareness with the 8u131 / 8u191 / 8u372 and 11.0.16 boundaries encoded correctly; flags that were removed and now abort startup; and heap-versus-limit budget arithmetic.

HPA correctness. The scaling arithmetic — ceil(current × util / target) with the ±10% tolerance dead-band — is correct, and it catches the spec.replicas-fights-the-HPA-on- upgrade bug, the memory-metric-on-a-JVM ratchet, dangling scaleTargetRef, and quoted-string numerics.

Accurate reference data. The deprecated and removed API table — 50 entries — matches the official Kubernetes migration guide, and the 512m milli-byte and bare-integer byte-scale typos are caught.

It knows when its own render was not evidence. With helm present it renders at both ends of the chart's declared kubeVersion range and diffs the emitted (kind, name) sets, so an object that exists at one end and not the other is reported as version-dependent rather than as fact.

JVM detection is a heuristic with a floor

It reads pod-spec env (JAVA_TOOL_OPTIONS, JDK_JAVA_OPTIONS, _JAVA_OPTIONS, JAVA_HOME, CATALINA_*, SPRING_*), image names (openjdk, temurin, corretto, zulu, graalvm, *-jre, *-jdk, tomcat, jetty, wildfly) and any Dockerfile's FROM line and flags.

The floor A Java service whose flags are baked into an opaque corp.registry/payments-api:4.2, with nothing Java-shaped in its name or pod spec, is invisible — and that is the most common real-world shape. What changed at R8 is not that this is solved but that the tool stopped guessing: the JAVA category reads NOT ASSESSED and the reason lists every input it examined, so you can see which one to add. Measured by proof/p8b_bar2.py CLAIM 6.

It cannot see your cluster

LimitRange defaulting — which can turn a "no requests" finding into a false positive — ResourceQuota, whether metrics-server or a custom-metrics adapter is installed, and the real node shape are all invisible. The report's Verify on your cluster section gives you the commands for each gap. Run them; they are the point of the section.

Static mode approximates Helm

Without helm on PATH, tpl, printf, required and subcharts cannot be resolved, and conditionals are analyzed as taken. Install helm for rendered-truth analysis. The report always states which mode ran, in the header and in every coverage row.

Estimates are estimates

The JVM memory-budget components — metaspace, JIT code cache, thread count, direct buffers, GC/internal — are DERIVED guesses. Each carries a documented band with a cited source, the peak-RSS total is reported as an interval, and when your limits.memory falls inside that interval the verdict is UNDETERMINED rather than either endpoint's answer. The report then names the smallest set of estimates that would flip it, how far they must move against the gap available, and the jcmd VM.native_memory command that settles it. Feed the result back with --measured and the estimates drop out.

What that does not fix The bands themselves are constants somebody chose. An app with a large dependency graph or a bytecode-weaving agent can sit outside them, and there the tool is confidently wrong in the old way — it merely states a range while being wrong. Measured by proof/p9b_bar2.py CLAIM 9.

Your PATH changes the answer

With helm absent, the same chart's Analysis mode drops to static, every coverage row is rewritten from rendered by helm to statically parsed, and finding HP050 loses a word. Two people on the same commit can therefore hold different reports and neither is wrong.

The container path pins the four binaries and makes that variable explicit. It does not make the pinned answer the right one for your cluster's Helm.

--cross-check does not reproduce

Measured, unfixed The cross-check section reshuffles between identical runs, natively. Every batch of four consecutive native runs over fixtures/bad-chart has produced four distinct md5 sums. The size of the disagreement is itself unstable: across three separate measurement rounds the pairwise diffs were 51, 55 and 65 lines; then 43, 44, 46, 48, 51 and 55; then 25, 30, 44, 48, 51 and 59 — and the proof script's own run of the same check once measured 70. Take the honest envelope as roughly 25 to 70 lines, not a figure. kube-score printed six distinct outputs over six runs of the same chart; polaris printed two over three. The cause is Go map iteration order in the tools being quoted.

No verdict or tally moves — those are count-based — but the evidence underneath them does. Do not diff two --cross-check reports and read meaning into the diff. Diff the runs without it.

This was found by accident while trying to prove something else, and it is not caused by containers. external.py reproduces external tool output verbatim by design, so "fixing" this means reordering another tool's words — a decision this project has not made. It is logged as R11 in docs/ITERATIONS.md, not solved.

This paragraph has now been widened twice by its own evidence. The first draft quoted 45 to 57 lines. Re-measuring returned 51 to 65, so it was corrected. Then proof/p11_docsite.py — which re-runs the measurement instead of repeating the number — observed a 25-line diff and a 59-line one in a single batch, refuting the 51 floor as well. Both superseded ranges are named here rather than quietly overwritten, because a document that revises its evidence silently is not evidence. The lesson is the one the numbers keep teaching: this is unbounded reshuffling, and any narrow range quoted for it is a sampling artefact waiting to be refuted.

Verification of the ecosystem paths is uneven, and here is how

All four external validators are exercised against the real binaries over real directories in tests/test_renderplan.py and tests/test_preflight_external.py, and those tests skip rather than mock when the binary is absent. Each verdict is checked against the tool's full output, obtained through the same argv builder the tool itself uses, so a test cannot pass judgement on a command line that is never run.

Until R6, kube-score and polaris had never been run by any test in any iteration, and both were misreported. The fix is why the report now prints a status derived from: line under each tool. tests/test_helm_mode.py still substitutes a canned render on purpose: it tests mode selection logic, not helm. Tool versions differ — confirm against your own installed versions before relying on them in CI.

Scope is deliberately narrow

One chart per run. It is a JVM/HPA/resources linter, not a general Kubernetes validator, a schema checker, or a security scanner.

Subcharts are not graded. A vendored chart is someone else's code, and folding its findings into your score would misrepresent what you are responsible for. What changed at R7 is that the boundary no longer functions as evidence: until then the objects helm template rendered from charts/ were discarded, so a rule could not see a Deployment helm had just produced from charts/worker and reported the user's correct HPA as dangling at HIGH, labelled OBSERVED. Followed, its Fix: line retargeted a working HPA onto the wrong workload — and the tool then called the broken chart clean. Those objects are now recorded but never scored, and the coverage table names the subchart, its kinds and its object names.

The cost Where subcharts exist but did not render — static mode, or a subchart gated off by a condition — a target the tool cannot find is reported as UNDETERMINED rather than as a finding. Which means a genuinely dangling reference in an umbrella chart analysed without helm will not be flagged. That is a real loss, taken deliberately, and the coverage row says which claim went unchecked and how to settle it.

Do not assume

A high grade does not mean "deployable." An A+ is a statement about the files, by static analysis. It is not a promise the workload will schedule, scale, or even be admitted on your cluster.

It does not replace your existing tools. Run it alongside kubeconform for schema, a policy engine — Kyverno, OPA, or ValidatingAdmissionPolicy — for org rules, and a real load test. Use --fail-on high as a warning gate, not as the sole merge blocker.

Absence of a finding is not proof of correctness. It can mean "not covered." Read the coverage section.

The proof-table numbers are arithmetic on estimates, not measurements.

A finding's severity accounts for the cluster version your chart declares, and nothing else about your cluster. Deprecated-API severity is reconciled against kubeVersion: the same networking.k8s.io/v1beta1 Ingress is CRITICAL with no declared range or a modern one, and LOW under >=1.19.0-0 <1.21.0-0, a range where the API still exists. Namespace LimitRange, quota and metrics setup are invisible and are in no severity at all.

The external-validator output is not ours. --cross-check runs those tools and reports their output verbatim; this project does not vouch for it.

It does not know a Java version the base-image tag hides. Pass --assume-java <ver> for internal or corporate base images. Since R8 this no longer skips the JVM checks wholesale — heap-versus-limit arithmetic needs only the flags and the limit, and runs without it. What degrades is the version-dependent subset, and the report says which. Note also that this flag asks you for something usually sitting in your repository already, in pom.xml, build.gradle or .java-version; reading it from there is queued, not done.

Running it in the container makes the answer reproducible, not correct. The image pins helm 3.16.4 and three validators; if your cluster runs a different Helm, the pinned render is reproducibly the wrong one and the tool cannot tell. Nor was the shipped image itself proven equivalent to a native run — the byte-identity measurement used a locally assembled stand-in, because no registry was reachable from the machine this was built on. The container page says exactly what that does and does not establish.

A NOT ASSESSED category is not a pass, and a missing finding is not either. The tool deliberately prints "the JVM checks did not apply, and here is what would make them apply" rather than going quiet, because in a report that only lists failures, an unrun check and a passed check look identical.

If any of the above matters to you, the tool is designed to help you check it rather than take its word — that is what the basis labels, the coverage section, and the "Verify on your cluster" commands are for.
