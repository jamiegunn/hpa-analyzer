Reading the report

A default report is around 900 lines and has seven numbered sections. This page says what each one is for, and — more usefully — which parts of it you are most likely to misread.

The seven sections

In order, with a header block above them naming the target directory, the timestamp, the chart, and every file that was actually read:

#SectionWhat it is
1Executive summaryScore, grade, counts, and the fix-first list
2Analysis coverageWhat was and was not checked, per input
3Scorecard by categoryTen categories, each with score, grade, weight and finding counts
4Findings and remediationGrouped by severity, each with basis, math and a fix
5Mathematical proof tablesThe arithmetic, shown rather than asserted
6Verify on your clusterCommands for the gaps static analysis cannot close
7Methodology and limitationsHow it decided what it decided

Two variations. With --full an education appendix is inserted as section 7 and methodology becomes 8. With --cross-check the external-validator section takes slot 7 and methodology moves down. The numbers shift; the content does not disappear.

1 · The score, and its scale

  OVERALL QUALITY SCORE :  45.5 / 100   GRADE: F
  [#######################...........................]

  What this number is: a weighted count of what THIS TOOL found. Each category starts
  at 100 and loses points per finding. It is not an estimate of risk and not a
  prediction that the service will hold up - a chart can score 100 and still fall
  over, because only the things the tool knows how to look for can subtract.

  Computed over         : all 10 categories (100 of 100 weight points)
  Analysis mode         : helm

The line that does the real work is Computed over. The overall score is a weighted mean across the categories that could be assessed. A category the tool could not assess is not scored 0 and not scored 100 — there is no honest number for "not looked at" — so it leaves the mean entirely, numerator and denominator together. That renormalises everything else.

Which means: two scores are comparable only when their category counts match. The report prints the count next to the score for exactly this reason, and --require-coverage is how you enforce it in CI.

The deduction model is fixed and stated in the report: each category starts at 100 and loses 25 per CRITICAL, 12 per HIGH, 6 per MEDIUM, 3 per LOW, 0 per INFO, floored at 0.

2 · Coverage: what was not checked

This is the section people skip and should not. Its opening sentence is the whole argument:

Findings can only come from files that were successfully analyzed. Anything marked as failed, skipped or unknown below produced NO findings — treat that as missing coverage, never as a clean bill of health.

In a report that lists only failures, an unrun check and a passed check look identical. The coverage table is what separates them: a row per input, saying whether it was rendered by helm, statically parsed, or not read at all — and when it names a subchart, it names the subchart's kinds and object names rather than counting them.

A category can read NOT ASSESSED. That is not a pass. It means the inputs that category needs were absent — and the reason line will list every input that was examined, so you can see which one to add.

4 · Findings, and the basis label

Every finding carries the same anatomy: category and file, a basis, what was found, why it matters, the math where there is any, and a fix.

[HP004] HPA minReplicas > maxReplicas (invalid)
    Category: Horizontal Pod Autoscaling | templates/hpa.yaml
    Basis : OBSERVED - read directly from your files (stated as fact).
    Found : [with values overlay values-prod.yaml] HPA 'release-name-payments':
            minReplicas=25 > maxReplicas=20.
    Why   : Invalid object - the API server rejects it, so the workload has NO
            autoscaling and helm upgrade fails.
    Math  : Constraint violated: 25 <= 20 is false.
    Fix   : Make min <= max.

The basis label is the tool's confidence, made explicit rather than implied by tone:

BasisMeansHow to treat it
OBSERVEDRead directly from your filesStated as fact. Act on it.
DERIVEDComputed from what was read, using a documented modelCheck the proof table it points at.
ASSUMEDCould not be observed; the tool fell back to a guessVerify before acting — an Assumes: line names the guess and says what happens if it is wrong.

An ASSUMED finding names its own escape hatch. Here is one, in full, from the same report:

[HP025] HPA scales on memory for a JVM workload
    Basis  : ASSUMED - the tool could not observe this directly and fell back to a
             guess; verify before acting (see Assumes).
    Assumes: the workload this HPA targets is the Java service (inferred from a single
             workload + a Java Dockerfile; the HPA's target was not resolvable by name)
             - if that is wrong, this finding does not apply.

That finding is also a fair example of what the tool is for. Its Why is not "memory metrics are discouraged" but an argument: a JVM's committed heap stays near its high-water mark, so measured utilisation stays high after load drops, so the scale-down condition is unreachable and the HPA ratchets to maxReplicas and stays there. The Math line then shows the inequality that never becomes true.

5 · The proof tables

Seven tables in a typical run. They exist so you can disagree with the tool using arithmetic rather than intuition. The JVM memory budget is the one to read first:

Container memory must hold the WHOLE JVM, not just the heap. Estimation model:
T = H + Metaspace + CodeCache + threads*Xss + DirectBuffers + GC/internal.
JVM visibility of the limit: 8u151 without applied experimental cgroup flags.

+--------------------------+-------------------+------------------------------------------+
| Component                | Size              | Basis                                    |
+==========================+===================+==========================================+
| Container memory limit   | NOT SET           | -                                        |
| Max heap (H)             | 4 GiB             | JVM CANNOT see the limit (8u151 without  |
|                          |                   | applied experimental cgroup flags);      |
|                          |                   | default 25% x assumed node RAM 16 GiB    |
| Metaspace (est.)         | 128 MiB           | est. 128 MiB, range 80 MiB-180 MiB       |
| JIT code cache (est.)    | 64 MiB            | est. 64 MiB, range 32 MiB-128 MiB        |
| Thread stacks (est.)     | 100 MiB           | est. 100 MiB, range 50 MiB-200 MiB       |
|   Thread count (est.)    | 100 (est. 50-200) | Spring Boot's embedded Tomcat defaults   |
|                          |                   | to server.tomcat.threads.max=200         |
|   Thread stack size      | 1 MiB             | HotSpot default on Linux x86-64; a       |
|                          |                   | documented platform default, not an      |
|                          |                   | estimate, so its band has zero width     |
| Direct buffers (est.)    | 64 MiB            | est. 64 MiB, range 16 MiB-128 MiB        |
+--------------------------+-------------------+------------------------------------------+

Real table for fixtures/bad-chart, abridged. Every estimate carries a band and a cited reason for the band.

Note what the "Max heap" row is doing. The Dockerfile says Java 8u151, which predates container-awareness being on by default, so the JVM cannot see the cgroup limit and sizes its heap from the node's RAM instead — 25% of an assumed 16 GiB, giving a 4 GiB heap inside a container that was never given a memory limit at all. That is the class of bug this tool exists to find, and the table is how it shows its working.

Components marked (est.) are estimates. Feed real numbers back with --measured and they become OBSERVED and drop out of the range. And keep the honest framing in view: the proof-table numbers are arithmetic on estimates, not measurements.

6 · Verify on your cluster

The tool reads files, not a cluster. This section lists each real Kubernetes behaviour it cannot see, with the command that closes the gap and instructions for reading the answer. Only the checks relevant to your chart appear, with names and selectors filled in:

[metrics-pipeline] Will the HPA actually scale?
    Gap  : Static files cannot show whether metrics-server / a custom-metrics adapter
           is installed, or the HPA's live status.
    Run  :
        $ kubectl describe hpa release-name-payments -n <namespace>
        $ kubectl top pods -n <namespace> -l app=payments
    Read : In `describe hpa`, the Conditions block must show `ScalingActive True`.
           `AbleToScale False` / `FailedGetResourceMetric` means the metrics API is not
           serving this HPA - install/repair metrics-server.

The limitrange probe in the same section matters more than it looks: a namespace LimitRange can inject requests and limits that this report flags as absent, changing the real QoS class. A "no requests" finding can be a false positive for exactly that reason, and the tool cannot see it from your files.

The three ways the grade will mislead you

One It is a count of what this tool found, not a measure of risk. Nothing subtracts for a problem the tool has no rule for. A chart can score 100 and still fall over.

Two It is not comparable across runs by default. Losing an input removes a category and renormalises the mean. Compare only when the "computed over" counts match, and enforce that with --require-coverage.

Three An A+ is a statement about the files. It is not a promise the workload will schedule, scale, or even be admitted on your cluster. Note that fixtures/good-chart scores 100.0 and carries an UNDETERMINED JVM fit verdict at the same time — the report says outright that this is "not scored, and NOT a pass".
