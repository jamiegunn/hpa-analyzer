Confirm it found your files

Run --check first, every time you point the tool at a new directory. It reports what it discovered, flags anything misplaced, and exits without analyzing.

hpa-analyzer ./my-service --check

Exit 0 means it found a chart it can work with — possibly with warnings. Exit 2 means it is not a chart directory and analyzing would be theatre. The check also names the render mode it is about to use, which is the earliest point at which you can notice that helm is missing.

Why A report is only as good as its inputs, and a static analyzer that silently reads nothing produces a clean report. --check is the cheapest way to find out that your values file is named something the tool did not look for.

Choose how much detail

Four settings, from triage to teaching. Line counts below are the real report sizes for fixtures/bad-chart (60 findings), so the ratios are honest rather than illustrative. They were measured with helm on PATH; see the note under the table if yours are longer.

FlagReportLinesUse it when
--summaryScore, scorecard, and the top CRITICAL/HIGH findings only171You want the triage list and nothing else
(default)Everything, with LOW/INFO collapsed to one line each910Normal use
--allLOW/INFO expanded to full detail1022You are doing a full pass and want the small stuff too
--fullEverything plus the education appendix (implies --all --teach)1242You are handing this to someone who has not met cgroups yet

Your numbers may differ Those four figures are a helm-mode run. On a machine with no helm the same four commands over the same chart produce 174, 923, 1035 and 1255 lines — the report is longer because static mode adds the parse-problem warning and rewrites every coverage row to say what was parsed rather than rendered. This was measured by running the same commands on a second machine that happens not to have helm, not estimated.

For this chart the verdict did not move — GRADE F, 45.5/100, the same 60 findings, the same top five. That is a property of this fixture, not a guarantee: static mode is a weaker reading of a chart, and the tool says so on its own banner rather than leaving you to notice. Compare mode: helm with mode: static (helm not found on PATH) on the last line of the terminal summary before comparing anything else.

--summary and --full are mutually exclusive; argparse rejects the pair. Two independent knobs sit underneath: --all expands the quiet findings, and --teach appends the HPA/JVM primer as its own section. --full is exactly both.

Separately, --quiet changes only the terminal output — one line instead of the banner and the fix-first list — and leaves the report file untouched:

$ hpa-analyzer fixtures/good-chart --quiet
hpa-analyzer [helm]: score 100.0/100 (grade A+), 0 finding(s) -> /home/you/hpa_analysis_report.txt

--stdout is the opposite: it prints the whole text report to standard output as well as writing the file.

Get HTML or JSON out

The text report is always written. The other two formats are additive.

hpa-analyzer ./my-service -o reports/svc.txt --html --json reports/svc.json

--html takes an optional path. Given none, it derives one from -o by swapping the extension — the command above writes reports/svc.html. The HTML report is a single self-contained file with a table of contents, collapsible sections and a severity filter; open it in a browser, no server needed.

Careful --html's argument is optional, which means --html --summary ./chart would let --html swallow --summary. Put --html last, or give it an explicit path. The container wrapper is tested specifically against this case (see how the wrapper reads your command line).

--json writes the machine-readable form. Top-level keys are target, mode, score, grade, graded, score_coverage, counts, findings, coverage, cluster_probes, preflight and cross_check. Each finding looks like this:

{
 "rule": "CH002",
 "severity": "MEDIUM",
 "basis": "observed",
 "assumes": null,
 "category": "Helm Chart Structure & Hygiene",
 "title": "Chart apiVersion v1 (Helm 2 era)",
 "file": "Chart.yaml",
 "line": null,
 "detail": "Chart.yaml declares apiVersion: v1.",
 "why": "apiVersion v1 targets Helm 2, which reached end of life in Nov 2020 ...",
 "fix": "Set apiVersion: v2 and manage dependencies via the 'dependencies' key ...",
 "math": null
}

A real finding from fixtures/bad-chart. severity is one of CRITICAL, HIGH, MEDIUM, LOW, INFO; basis is one of observed, derived, assumed. Full shape on the reference page.

Gate a pipeline on it

Three flags can turn a run into a failure. All of them exit 1; nothing else does.

hpa-analyzer ./svc --fail-on high --json reports/hpa.json --quiet
FlagExits 1 when
--fail-on {none,low,medium,high,critical}Any finding exists at or above that severity
--min-score NThe score is below N — or the run was ungradeable
--require-coverageAny scoring category could not be assessed

Measured, so you can trust the table: --fail-on high against fixtures/bad-chart exits 1 and prints gate: findings at or above --fail-on=high exist; the same flag against fixtures/good-chart exits 0; --require-coverage against fixtures/nojvm-chart exits 1, because that chart runs no JVM so the JAVA category cannot be assessed.

Use both --min-score alone is a trap. The score is a weighted mean over the categories that could be assessed, so deleting an input — the Dockerfile, say — removes a category, renormalises the mean, and silently changes the scale your threshold is compared against. A chart can cross your threshold by losing a file. Pair --min-score with --require-coverage and that stops being possible.

And keep this in proportion: --fail-on high is a warning gate, not a merge blocker. It is a count of what one linter found, and Limits explains what it cannot count.

Settle an UNDETERMINED verdict with real numbers

The JVM memory budget is built from five estimated components — metaspace, JIT code cache, thread stacks, direct buffers and GC/internal overhead. When your limits.memory falls inside the resulting range, the tool refuses to pick an endpoint and says so:

$ hpa-analyzer fixtures/good-chart
  GRADE A+  (100.0/100)   0 critical, 0 high, 0 medium, 0 low
  JVM fit UNDETERMINED (limit 1 GiB vs model range 722 MiB-1.2 GiB) for Deployment
  'release-name-orders-service' / container 'orders' - not scored, and NOT a pass.
  Settle it with `--measured metaspace=...,codecache=...,threads=...,direct=...,gc=...`.

Get the real numbers off a running pod with jcmd <pid> VM.native_memory summary (the report prints the exact command in its Verify on your cluster section), then feed them back. A measured component becomes OBSERVED, drops out of the range, and can no longer make the verdict undetermined.

$ hpa-analyzer fixtures/good-chart --measured metaspace=210Mi,threads=180
  GRADE A+  (98.3/100)   0 critical, 1 high, 0 medium, 0 low
  JVM fit UNDETERMINED (limit 1 GiB vs model range 982 MiB-1.2 GiB) ...
  Fix first:
    1. [XF002] Estimated JVM footprint exceeds memory limit at typical non-heap values

Real, and worth sitting with. Two measurements narrowed the range from 722 MiB–1.2 GiB to 982 MiB–1.2 GiB, which pushed the typical case above the 1 GiB limit and surfaced a HIGH finding that the wider range had been hiding. The score went down, from 100.0 to 98.3, because better information found a real problem. That is the flag working, not the flag misbehaving.

Sizes take Ki/Mi/Gi or k/M/G; threads is a plain count. Valid keys: metaspace, codecache, threads, direct, gc, xss.

Control how the chart is rendered

--helm auto is the default: use the binary if it is on PATH, fall back to static parsing if it is not. --helm on requires it. --helm off forces static mode even when helm is available, which is mostly useful for reproducing what a colleague without helm is seeing.

--kube-version deserves more attention than it usually gets:

hpa-analyzer ./svc --kube-version 1.31.0

It is passed straight to helm template --kube-version, and it says which Kubernetes version the chart is being rendered for. Without it, the tool derives one from the chart's own kubeVersion; without that either, helm falls back to its compiled-in v1.20.0, which is long EOL and will refuse most modern charts. If a render fails for reasons that make no sense, this is the first flag to try.

Cross-check against the standard stack

hpa-analyzer ./svc --cross-check

This runs helm lint, kubeconform, kube-score and polaris — whichever are on your PATH — and folds their verbatim output into a section of the report, with a three-state status per tool:

+-------------+---------+-------------------------------------------------------------+
| Tool        | Status  | Result / reason                                             |
+=============+=========+=============================================================+
| helm lint   | FAIL    | Error: 1 chart(s) linted, 1 chart(s) failed                 |
+-------------+---------+-------------------------------------------------------------+
| kubeconform | UNKNOWN | 1 valid, 0 invalid, 2 not checkable, 0 skipped              |
+-------------+---------+-------------------------------------------------------------+
| kube-score  | FAIL    | 3 object(s) scored: 9 critical, 2 warning                   |
+-------------+---------+-------------------------------------------------------------+
| polaris     | FAIL    | score 66/100 over 1 controller(s): 3 danger, 12 warning     |
+-------------+---------+-------------------------------------------------------------+

Real output against fixtures/bad-chart, abridged to fit. Each tool's raw output is printed underneath, along with a run it yourself: line giving the exact command.

Two design decisions in that table are worth knowing. Status is not the exit code. Polaris exits 0 whether it found nothing or found danger, and kube-score exits 1 both when it dislikes a manifest and when it could not parse one — so status is derived from each tool's own printed tally, and a status derived from: line under each tool names the signal that was read. UNKNOWN is a third state on purpose. It means the validator ran and could not reach a verdict, usually because it could not fetch a schema. Reporting that as FAIL would tell you your manifests are broken when nothing was actually checked.

Measured The cross-check section does not reproduce between identical runs, and containers are not the cause. Four consecutive native runs over fixtures/bad-chart produce four distinct md5 sums every time, differing by roughly 25 to 70 lines depending on the run — the size of the disagreement is not stable either. The statuses and tallies are count-based and stay put — no verdict moves — but the evidence printed underneath reshuffles, because the tools being quoted iterate Go maps. Do not diff two --cross-check reports and read meaning into the diff. Diff the runs without it. Details in Limits.

When the base image hides the Java version

A tag like corp.registry/payments-api:4.2 tells the tool nothing about which JDK is inside. Supply it:

hpa-analyzer ./svc --assume-java 17

Accepts 8, 8u151, 11.0.16, 17 and similar. Without it the tool does not skip the JVM checks wholesale — heap-versus-limit arithmetic needs only the flags and the limit, and still runs. What degrades is the version-dependent subset: the 8u131 / 8u191 / 8u372 and 11.0.16 cgroup-awareness boundaries. The report states which checks were reduced.

Worth saying plainly: this flag asks you for something that is usually sitting in your repository already, in pom.xml, build.gradle or .java-version. Reading it from there is queued work, not done work.
