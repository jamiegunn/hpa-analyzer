TABLE 6: Availability vs replica floor
----------------------------------------------------------------------------------------------------
Redundancy math for the minimum number of pods the chart allows to exist.

+------------+------------------------+------------------------------------+
| Replicas n | Availability 1-(1-p)^n | Expected downtime                  |
+============+========================+====================================+
| 1          | 99.500000%             | ~216.0 min/month                   |
+------------+------------------------+------------------------------------+
| 2          | 99.997500%             | ~1.1 min/month                     |
+------------+------------------------+------------------------------------+
| 3          | 99.999988%             | ~0.32 sec/month  <-- current floor |
+------------+------------------------+------------------------------------+
| 5          | 100.000000%            | ~0.00 sec/month                    |
+------------+------------------------+------------------------------------+

  VERDICT: Assuming INDEPENDENT pod failures at 99.5% per-pod availability, availability =
  1-(1-p)^n. Your scale floor is n=3 (HPA minReplicas). n>=2 keeps single-failure downtime
  negligible; protect it with a PDB. Caveat: the independence assumption is exactly what fails in
  correlated events (bad deploy, node/zone outage, shared dependency down) - those hit ALL
  replicas at once and no exponent helps. Treat this table as the upper bound that redundancy
  alone can buy.

[resourcequota] Could a namespace quota reject this workload?
----------------------------------------------------------------------------------------------------
    Gap  : A ResourceQuota can reject an otherwise-valid pod; quotas live in the cluster, not
    the chart.
    Run  :
        $ kubectl get resourcequota -n <namespace> -o yaml
    Read : If `status.used` is near `status.hard` for cpu/memory/pods, the workload may be
    rejected at admission even though this chart is internally valid.

----------------------------------------------------------------------------------------------------
[jvm-sees-limit] Does the JVM actually see the cgroup limit?
----------------------------------------------------------------------------------------------------
    Gap  : The heap the JVM chooses at runtime depends on whether it can read the container
    limit - which depends on the JDK build and the node's cgroup version, neither fully knowable
    from files.
    Run  :
        $ kubectl exec -n <namespace> <release>-<pod> -- java -XX:+PrintFlagsFinal -version 2>/dev/null | grep -E 'MaxHeapSize|MaxRAMPercentage|UseContainerSupport|ActiveProcessorCount'
        $ kubectl exec -n <namespace> <release>-<pod> -- sh -c 'stat -fc %T /sys/fs/cgroup'   # cgroup2fs = cgroup v2
    Read : `MaxHeapSize` should be ~ (your memory LIMIT x the heap percentage), NOT ~1/4 of the
    node's RAM - the latter means the JVM is sizing from the host (old JDK or cgroup-v2
    blindness). `cgroup2fs` confirms a v2 node; verify your JDK supports it (8u372+ / 11.0.16+ /
    15+).
