[HP025] HPA scales on memory for a JVM workload
    Category: Horizontal Pod Autoscaling
    Basis : ASSUMED - the tool could not observe this directly and fell back to a guess; verify
    before acting (see Assumes).
    Assumes: the workload this HPA targets is the Java service (inferred from a single workload
    + a Java Dockerfile; the HPA's target was not resolvable by name) - if that is wrong, this
    finding does not apply.
    Found : HPA 'RELEASE-NAME-payments' includes a memory utilization/average-value metric
    (target 80%).
    Why   : Memory-utilization HPA assumes memory falls when load falls. A JVM violates that
    assumption: committed heap stays at or near its high-water mark (most collectors return
    memory to the OS reluctantly or never), so measured 'utilization' stays high after load
    drops. Result: the HPA scales UP under load but never scales back DOWN - it ratchets to
    maxReplicas and stays there.
    Math  : Example with Xmx-bound JVM: after warmup RSS ~= heap_committed + off-heap ~=
    constant C. utilization = C/request stays > 80% regardless of traffic => desired =
    ceil(current x util/80) >= current forever (HPA tolerance +/-10%). Scale-down condition util
    < 80% is unreachable.
    Fix   : Scale JVMs on CPU or on a load-proportional metric (requests/sec via external
    metrics, queue depth). If memory must gate scaling, use it only as a secondary metric and
    remember HPA takes the MAX of all metric proposals - memory will dominate.

[HP050] Deployment sets spec.replicas while an HPA manages it
    Category: Horizontal Pod Autoscaling | templates/deployment.yaml:7
    Basis : OBSERVED - read directly from your files (stated as fact).
    Found : Deployment 'RELEASE-NAME-payments' sets spec.replicas=2 with no guard at all, AND an
    HPA targets this workload.
    Why   : Helm and the HPA now fight over the same field. Every 'helm upgrade' resets replicas
    to the template value; if the HPA had scaled to 10 and the template says 2, the deploy
    instantly kills 8 loaded pods mid-traffic. The HPA scales back up minutes later - after your
    users noticed.
    Math  : Upgrade at peak: pods 10 -> 2 (helm apply) => per-pod load x5 instantly; if pods

    startup).
    Fix   : Omit spec.replicas entirely when autoscaling is enabled:
            {{- if not .Values.autoscaling.enabled }}
            replicas: {{ .Values.replicaCount }}
            {{- end }}

[RS002] Memory quantity uses 'm' (MILLI-bytes)
    Category: Resource Requests & Limits | values.yaml:15
    Basis : OBSERVED - read directly from your files (stated as fact).
    Found : Deployment 'RELEASE-NAME-payments', container 'payments': requests.memory = '512m'.
    Why   : Lowercase 'm' is a legal Kubernetes suffix meaning 1/1000 of a byte. '512m' is 0.512
    BYTES, not 512 MiB. As a request it schedules the pod as if it needs nothing; as a limit the
    container is OOM-killed on its first allocation.
    Math  : '512m' = 0.512 bytes; '512Mi' = 536,870,912 bytes - a factor of 1000 x 1024^2 ~=
    1.05 billion.
    Fix   : Use '512Mi'.

[HP023] HPA CPU target 95% leaves no scaling headroom
    Category: Horizontal Pod Autoscaling | templates/hpa.yaml
    Basis : OBSERVED - read directly from your files (stated as fact).
    Found : HPA 'RELEASE-NAME-payments' targets averageUtilization=95%.
    Why   : Scaling is not instantaneous: metrics lag (15-60s), pods schedule, images pull, and
    a JVM warms up. During that window existing pods must absorb the excess ABOVE the target. At
    95% the buffer before saturation is only 5%.
    Math  : Absorbable load growth while scaling = 100/95 - 1 = 5%. With a 90s JVM startup, load
    growing faster than 5% per ~2 min saturates pods before help arrives.
    Fix   : Target 60-75% for JVM services; lower if startup is slow.

[RS005] No memory limit
    Category: Resource Requests & Limits | templates/deployment.yaml
    Basis : OBSERVED - read directly from your files (stated as fact).
    Found : Deployment 'RELEASE-NAME-payments', container 'payments': limits.memory is not set.
    Why   : Memory is incompressible: when a node runs out, the kernel OOM-killer picks victims.
    An unlimited JVM with a native leak or unbounded -Xmx can evict every other pod on the node.
    For JVM workloads a memory limit is the container's contract with the JVM's
    container-awareness (MaxRAMPercentage is computed FROM it).
    Fix   : Set limits.memory (commonly = requests.memory for JVMs, giving Guaranteed-style
    memory QoS).

[JV001] Java 8 runtime
    Category: Java / JVM Container Fitness | Dockerfile
    Basis : OBSERVED - read directly from your files (stated as fact).
    Found : Base image openjdk:8u151-jdk is Java 8 (update 151).
    Why   : Java 8 (2014) predates containers: its container support is a chain of backports
    with sharp edges (see the related findings), it lacks modern collectors (G1 improvements,

[JV013] Java 8u151: blind to cgroup v2 nodes
    Category: Java / JVM Container Fitness | Dockerfile
    Basis : OBSERVED - read directly from your files (stated as fact).
    Found : cgroup v2 support reached Java 8 at 8u372.
    Why   : Modern node OSes (Ubuntu >= 22.04, EKS AL2023, GKE COS, anything K8s ~1.25+) default
    to cgroup v2. On such nodes this JVM finds no cgroup v1 files, concludes it is NOT in a
    container, and reverts to host-RAM/host-CPU sizing - re-introducing the OOM-kill behavior of
    pre-container-aware JVMs even though UseContainerSupport is 'on'.
    Fix   : Upgrade to 8u372+ / 11.0.16+ / 17+, or pin explicit -Xmx and
    -XX:ActiveProcessorCount as a stopgap.

[JV021] No JVM heap sizing is actually applied
    Category: Java / JVM Container Fitness | Dockerfile
    Basis : OBSERVED - read directly from your files (stated as fact).
    Found : Neither -Xmx nor -XX:MaxRAMPercentage/-XX:MaxRAMFraction is applied. Heap sizing
    flags DO exist in an env var, but nothing applies them (see DF013) - the JVM runs on pure
    defaults.
    Why   : Without an applied heap bound the JVM uses its ergonomic default: 25% of the memory
    it can see. Two consequences: (a) most of the container memory you pay for is never used for
    heap, and (b) if the JVM cannot see the limit (old JDK, cgroup v2 mismatch - see other
    findings) that 25% is 25% of the NODE.
    Math  : Default heap = 0.25 x visible_RAM. Container limit 1 GiB => heap 256 MiB (why so
    small?). No visible limit on a 64 GiB node => heap 16 GiB (why so large?) -> OOMKill.
    Fix   : Apply -XX:MaxRAMPercentage=50-75 (container-aware JDKs) or an explicit -Xmx ~ 50-75%
    of limits.memory, via a mechanism that actually reaches the JVM (JAVA_TOOL_OPTIONS, or
    exec-form expansion).

[PB004] Liveness can kill a still-starting JVM
    Category: Health Probes & Lifecycle | templates/deployment.yaml
    Basis : OBSERVED - read directly from your files (stated as fact).
    Found : Deployment 'RELEASE-NAME-payments', container 'payments': no startupProbe and
    liveness initialDelaySeconds=5s.
    Why   : JVM apps routinely need 30-120s+ to start (class loading, JIT, Spring context,
    connection pools) - especially with small CPU requests. If liveness fires before the app can
    answer, kubelet kills it, the restart is even slower (cold cache + CPU contention), and the
    pod enters CrashLoopBackOff without ever being unhealthy.
    Math  : Worst-case time-to-kill = initialDelay(5) + period(5) x failureThreshold(3) = 20s. A
    JVM needing more than 20s to start NEVER becomes live.
    Fix   : Add a startupProbe (e.g. periodSeconds=5, failureThreshold=36 -> up to 180s grace) -
    liveness only begins after startup succeeds.

5. MATHEMATICAL PROOF TABLES
====================================================================================================

Every table below derives its verdict from arithmetic on values found in YOUR files (estimates are
labeled and conservative). Re-check any number by hand.

----------------------------------------------------------------------------------------------------
TABLE 1: JVM memory budget - Deployment 'RELEASE-NAME-payments' / container 'payments'
----------------------------------------------------------------------------------------------------
Container memory must hold the WHOLE JVM, not just the heap. Estimation model: T = H + Metaspace +
CodeCache + threads*Xss + DirectBuffers + GC/internal. JVM visibility of the limit: 8u151 without
applied experimental cgroup flags.

+-----------------------------+---------+----------------------------------------------------------+
| Component                   | Size    | Basis                                                    |
+=============================+=========+==========================================================+
| Container memory limit      | NOT SET | -                                                        |
+-----------------------------+---------+----------------------------------------------------------+
| Max heap (H)                | 4 GiB   | JVM CANNOT see the limit (8u151 without applied          |
|                             |         | experimental cgroup flags); default 25% x assumed node   |
|                             |         | RAM 16 GiB                                               |
+-----------------------------+---------+----------------------------------------------------------+
| Metaspace (est.)            | 128 MiB | typical framework app 80-180 MiB                         |
+-----------------------------+---------+----------------------------------------------------------+
| JIT code cache (est.)       | 64 MiB  | steady-state                                             |
+-----------------------------+---------+----------------------------------------------------------+
| Thread stacks (100 x 1 MiB) | 100 MiB | -Xss x thread count                                      |
+-----------------------------+---------+----------------------------------------------------------+
| Direct buffers (est.)       | 64 MiB  | est. 64 MiB typical                                      |
+-----------------------------+---------+----------------------------------------------------------+
| GC + JVM internal (est.)    | 48 MiB  | card tables, symbols                                     |
+-----------------------------+---------+----------------------------------------------------------+
| ESTIMATED PEAK RSS (T)      | 4.4 GiB | T = H + non-heap components                              |
+-----------------------------+---------+----------------------------------------------------------+

  VERDICT: No memory limit: the JVM competes with every pod on the node; a leak becomes the node's
  problem. Set a limit and size the heap from it.

----------------------------------------------------------------------------------------------------
TABLE 2: CPU as seen by the JVM - Deployment 'RELEASE-NAME-payments' / container 'payments'
----------------------------------------------------------------------------------------------------
Kubernetes CPU limits are CFS quotas; the JVM derives its parallelism from them.

+-----------------------+-------+------------------------------------------------------------------+
| Item                  | Value | Meaning                                                          |
+=======================+=======+==================================================================+
| CPU request           | 100m  | guaranteed share under contention; HPA denominator               |
+-----------------------+-------+------------------------------------------------------------------+
| CPU limit             | none  | pod may use idle node CPU                                        |
+-----------------------+-------+------------------------------------------------------------------+
| availableProcessors() | 1     | cpu.shares heuristic: ceil(request 100m / 1000m) - applies to    |
|                       |       | Java 8u151 (JDK 8 / pre-11.0.17). JDK 11.0.17+/17+ would instead |
|                       |       | see ALL node CPUs here.                                          |
+-----------------------+-------+------------------------------------------------------------------+
| Consequences          |       | sizes GC threads, ForkJoinPool, C2 compiler threads, Netty event |
|                       |       | loops                                                            |
+-----------------------+-------+------------------------------------------------------------------+

  VERDICT: No CPU limit: generally GOOD for JVMs (no CFS throttle); requests still guarantee fair
  share under contention.

----------------------------------------------------------------------------------------------------
TABLE 3: Probe budget vs JVM startup - Deployment 'RELEASE-NAME-payments' / 'payments'
----------------------------------------------------------------------------------------------------
A liveness probe that fires before the JVM can answer does not detect failure - it CAUSES it.

+------------------------------------+--------------+----------------------------------------------+
| Quantity                           | Value        | Note                                         |
+====================================+==============+==============================================+
| startupProbe window                | none         | liveness starts immediately                  |
+------------------------------------+--------------+----------------------------------------------+
| liveness initialDelaySeconds       | 5s           |                                              |
+------------------------------------+--------------+----------------------------------------------+
| liveness period x failureThreshold | 5s x 3 = 15s |                                              |
+------------------------------------+--------------+----------------------------------------------+
| Worst-case time-to-kill            | 20s          | init(5) + period(5) x failures(3)            |
+------------------------------------+--------------+----------------------------------------------+
| Typical JVM app startup            | ~60s         | mid-size Spring Boot on ~1 CPU (assumption;  |
|                                    |              | measure yours)                               |
+------------------------------------+--------------+----------------------------------------------+

  VERDICT: BUDGET 20s < startup ~60s: kubelet kills the pod BEFORE the app can come up; each
  restart is slower (CPU contention) => CrashLoopBackOff of a perfectly healthy build.

----------------------------------------------------------------------------------------------------
TABLE 4: QoS class and eviction order
----------------------------------------------------------------------------------------------------
QoS derivation: Guaranteed iff requests == limits for BOTH cpu and memory on every container;
BestEffort iff none set; else Burstable. Under node memory pressure kubelet evicts BestEffort, then
Burstable exceeding requests, then Guaranteed last.

+----------------------+---------+---------+---------+---------+-----------+-----------------------+
| Container            | req CPU | req Mem | lim CPU | lim Mem | QoS       | Eviction              |
+======================+=========+=========+=========+=========+===========+=======================+
| Deployment/RELEASE-N | 100m    | 0 B     | -       | -       | Burstable | evicted before        |
| AME-payments:payment |         |         |         |         |           | Guaranteed            |
| s                    |         |         |         |         |           |                       |
+----------------------+---------+---------+---------+---------+-----------+-----------------------+

  VERDICT: For latency-sensitive JVMs aim for Guaranteed memory (request = limit) and request-only
  CPU.

TABLE 5: HPA scaling arithmetic - HPA 'RELEASE-NAME-payments'
----------------------------------------------------------------------------------------------------
How the HPA converts measured CPU into replica counts (current replicas = 1 for illustration).

+-----------------+---------------+---------------------+-------------------+----------------------+
| Avg utilization | Per-pod usage | Raw formula         | Desired (clamped) | Action               |
+=================+===============+=====================+===================+======================+
| 48%             | 48m/pod       | ceil(1 x 48/95) = 1 | 1                 | no change            |
+-----------------+---------------+---------------------+-------------------+----------------------+
| 86%             | 86m/pod       | ceil(1 x 86/95) = 1 | 1                 | no change (within    |
|                 |               |                     |                   | 10% tolerance)       |
+-----------------+---------------+---------------------+-------------------+----------------------+

|                 |               |                     |                   | 10% tolerance)       |
+-----------------+---------------+---------------------+-------------------+----------------------+

|                 |               | 2                   |                   |                      |
+-----------------+---------------+---------------------+-------------------+----------------------+

|                 |               | 2                   |                   |                      |
+-----------------+---------------+---------------------+-------------------+----------------------+

TABLE 6: Availability vs replica floor
----------------------------------------------------------------------------------------------------
Redundancy math for the minimum number of pods the chart allows to exist.

+------------+------------------------+-------------------------------------+
| Replicas n | Availability 1-(1-p)^n | Expected downtime                   |
+============+========================+=====================================+
| 1          | 99.500000%             | ~216.0 min/month  <-- current floor |
+------------+------------------------+-------------------------------------+
| 2          | 99.997500%             | ~1.1 min/month                      |
+------------+------------------------+-------------------------------------+
| 3          | 99.999988%             | ~0.32 sec/month                     |
+------------+------------------------+-------------------------------------+
| 5          | 100.000000%            | ~0.00 sec/month                     |
+------------+------------------------+-------------------------------------+

  VERDICT: Assuming INDEPENDENT pod failures at 99.5% per-pod availability, availability =
  1-(1-p)^n. Your scale floor is n=1 (HPA minReplicas). n=1 concentrates ~100x more downtime than
  n=2 - redundancy, not pod quality, dominates availability. Caveat: the independence assumption
  is exactly what fails in correlated events (bad deploy, node/zone outage, shared dependency
  down) - those hit ALL replicas at once and no exponent helps. Treat this table as the upper
  bound that redundancy alone can buy.
